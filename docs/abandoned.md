# 放弃方案记录

> skill 要求：放弃了什么、证据、在什么条件下成立、重新考虑需要什么新证据。
> 本文件只记**已经做出「不做」决定的路线**；还没做的功能在 `docs/status.md`。
> 「放弃」不是永久结论 —— 条件变了就回来改这里，并追写一条重新考虑的理由。

---

## 1. 首版做充电控制（smb5 + smb1390 + HL6111R）

- **放弃范围**：v0.1 不做充电电流/电压控制，只做**只读电量**。
- **证据**
  - 厂商 `kona_defconfig`：`QPNP_SMB5`、`SMB1390_CHARGE_PUMP_PSY`、`HL6111R` 全部为下游独占。
  - 上游主线 7.2 无 `smb5` 充电器驱动（只有 `qcom_smb2` 等旧平台）；充电泵更没有。
  - 电量计另一条路可用：厂商 defconfig 有 `BATTERY_BQ27XXX` / `BQ27XXX_I2C`，与本机 FDT 的 `bq27541@55` 对得上，
    上游已有 `bq27xxx_battery_i2c`。
- **在什么条件下成立**：只要不做快充/温度管理，只读电量就够日常用。双系统下 Android 仍是主要充电环境。
- **重新考虑需要**：① 上游出现 smb5 驱动（或社区 sm8250 板已跑通充电），② 或用户明确要求「Linux 下能正常充电」成为 v0.2 必做项。
  二者任一出现，就把本条移到状态表。

## 2. 相机 / ISP

- **放弃范围**：首版及可见版本内不支持相机。
- **证据**：SM8250 的 ISP（camss/camnoc）主线支持不完整，`techpack/camera` 是下游私有框架；
  厂商包内也只有下游实现，没有可迁移到主线的上游对应物。
- **在什么条件下成立**：平板用途以桌面/阅读/视频播放为主，不用相机。
- **重新考虑需要**：上游 camss 对 sm8250 的 CSID/VFE 支持补齐（关注 linux-media 邮件列表），
  且社区有同 SoC 设备出图记录。

## 3. 用厂商开源包补板级设备树（面板时序 / GPIO / 供电）

- **放弃范围**：不从 `yt_k606f_s100101_210209_row_opensource` 抄任何板级数值。
- **证据**（2026-10-29 核验，见 `权威数据/厂商开源包价值评估报告.md`）
  - 包内 `arch/arm64/boot/dts/vendor/qcom/` 只有 3 个条目（目录 + 空 Makefile），
    `arch/arm64/boot/dts/qcom/` 连 `kona.dtsi`/`sm8250.dtsi` 都没有 → **构不出任何 dtb**。
  - 全树 grep `bladex|k606f`：源码内 0 命中（只有 defconfig 文件名）。
  - 包内内核是 **4.19.136（出厂首版）**，设备实际跑 4.19.157（后续 OTA），两者都不是板级 dts 来源。
- **在什么条件下成立**：本机运行时 FDT（`~/amp/fdt/fdt-clean.dts`）信息维度严格更强，且是权威源。
- **重新考虑需要**：拿到 ODM 的板级 dtsi 原始文件（不是这份裁剪过的开源包）。

## 4. 在 initramfs 里「抢跑」初始化 eDP 桥，等 msm 接管

- **放弃范围**：不在 msm probe 之前手工上电/配置 PSA8331 桥。
- **证据**（`权威数据/交叉核验-eDP桥假说.md` 第五节）
  - 厂商代码里桥初始化排在 `dsi_display_enable()` **之后**；`pre/post_ulps` 的命名说明它围绕 DSI ULPS 时刻设计。
  - 桥的 eDP 侧要链路训练，没有稳定 DSI 输入流时训练结果无效。
  - msm 接管会重上电 PHY、重锁 PLL、复位 DSI 控制器，桥侧已训练状态大概率失效。
  - 桥驱动接管面板 VCC / loadswitch / BOB / 背光，与主线 dts 的 `vddio` + `pwm-backlight` 会抢同一路电。
- **在什么条件下成立**：改成真正的 `drm_bridge` 后，由 DRM 的 `pre_enable` 逆序执行天然保证时序。
- **重新考虑需要**：只有在「桥做成 drm_bridge 后仍无法在正确时刻上电」这种已证伪的情况下才回来看这条。

## 5. 直接复用厂商 `techpack/display`（SDE/DSI 下游框架）排显示问题

- **放弃范围**：不用下游显示框架的代码去定位主线 `msm_dsi_manager` / `drm_bridge` 的问题。
- **证据**：两套框架不同源（下游 ctrl/phy 分层 vs 主线 `drm_bridge` 链）；`dsi_pll_7nm.c` 里只有 `DIGTOP_SPARE4`，
  没有 `DIGTOP_PWRDN_B` 上电逻辑，验证不了我们的 7nm PHY 补丁。
- **在什么条件下成立**：可以作为**语义参考**（例如 `split_link`、`master/slave` 的建模），但不能作为实现来源。
- **重新考虑需要**：不需要 —— 除非上游主线代码路径本身要改，那时以 dri-devel 结论为准。
