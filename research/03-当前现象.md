# 3. 当前现象

> 对应清单第 3 项：完全黑屏 / 背光亮但无图像 / 有图像但花屏偏移？能否 ADB/SSH 进入系统？是否已移植面板驱动？

## 现象判定

| 现象 | 实际情况 |
|---|---|
| 完全黑屏（一点不亮） | **不是** |
| **背光亮、无图像** | **是。** 人眼验收：屏是亮的（背光由我们的驱动点亮），但整屏**没有任何图像/彩条**，也没有花屏、没有偏移、没有撕裂 |
| 有图像但花屏/偏移 | **不是** |

> 补充：早期（B7/B10/B16 那几轮）曾看到 **Tux 企鹅一闪而过**，但那帧是 **ABL（bootloader）
> 留下的 DSI 视频流**被桥转发出来的，**不是**我们自己内核送出的像素。这个区别很关键。

## 显示链路已经到哪一步（机器证据）

| 环节 | 状态 |
|---|---|
| SoC DSI 控制器（两个） | ✅ 使能（`DSI_CTRL=0x1f1` ENABLE、`CLK_CTRL=0x23f`），PLL 锁定，4 lane 全 active |
| DSI 时序 | ✅ 与厂商 per-link 真值逐位一致（htotal 1124 / hpw 16 / hbp 12 / hfp 16） |
| DSI PHY（7nm） | ✅ 96 个寄存器与 Android 工作态逐字节对齐（仅 FRAC_DIV 有 0.01% 级差异） |
| eDP 桥 SN65DSI86（0x2C） | ✅ 配置成功：`0x0A=0x82`（DP PLL 锁）、`0x96=0x01`（链路训练完成） |
| 桥是否收到 DSI | ✅ **收到了**：`0x12=0x36`（检测到 DSI 时钟）、`0xF0=0x00`（无 SOT/EOT/contention 等 PHY 错误） |
| eDP/DP 输出 | ✅ **一直有输出**：DPCD `0x200=0x81` 稳定（TCON 收到稳定同步），DP 同步锁干净 |
| **像素内容** | ❌ **坏的**：桥报 `0xF1 bit5` CHA_INVALID_LENGTH_ERR（视频数据长度不匹配），DSI 侧伴随 FIFO overflow/underflow |
| 背光 | ✅ 能亮（B7 起人眼确认） |

**一句话**：桥、链路、DP 输出都是好的，**问题在"喂给桥的像素数据对不上帧"**。

## 当前核心问题（截至 B68）

### 双链：随机坏链

- `bonded` 双 DSI（左右各 1080×1350）时，**每次引导随机一条链成为"坏链"**（CHA 或 CHB 随机），
  坏链持续整个 boot 报 INVALID_LENGTH + FIFO 洪流，好链全程干净。
- 两链 `host_power_on` 相差约 **22 ms，大于 1 帧（16.7 ms）** → 怀疑**链间启动竞态**。

### 单链 bisect：display probe 静默挂死

- 为隔离竞态，把 dts 改成**单链**（2160 全走 dsi0）+ 桥单通道配置。
- 单链内核**不是崩溃，是静默挂死**：dmesg 静止在 ~36.7 s（dpu/dsi 依赖解析后、`dsi_bind` 之前），
  软锁死检测器随后 panic，但**控制台被挂死方持有的锁挡住，打不出字**，`panic=10` 后回 fastboot。
- 已把挂死点收窄到：**`psa8331.pre_enable` 返回之后、`dsi0` 的 `power_on/phy_enable` 之前**
  （DRM 桥链的 panel-bridge 一段）。

## 面板驱动是否已移植

**已移植。** `panel-lenovo-k606f.c`：
- 2160×1350 OLED，**无 DCS 初始化序列、无 DSC 压缩**；
- 双 DSI **split** 模式（每链路 1080×1350）；
- 时序取自厂商 DT（不是抄参考设备）；
- 当前为 builtin（`CONFIG_DRM_PANEL_LENOVO_K606F=y`），与技术债 #30 记录的"应=`=m`"不一致。

## 已经排除过的方向（别重复走）

1. **桥寄存器配置错误** —— 256 字节全图与 Android 工作态 0 差异（B23）。
2. **写错 I²C 地址** —— 已确认两颗芯片，59 条表写 `0x2C`、mux 4 条写 `0x33`（B39 修正）。
3. **PHY timing（clk_trail/clk_pre）** —— 修正后失败不变（B41）。
4. **byte_intf_clk 速率** —— 改为不除 2 后失败不变，已回滚（B43）。
5. **HS_TX_TIMEOUT 定时器** —— 设为厂商值后 TIMEOUT 消失，但 FIFO 错仍在（B42）。
6. **DSI 水平时序切分** —— 对齐厂商 1124/16/16/12 后失败不变（B32）。
7. **EOT 包** —— 去掉 `NO_EOT_PACKET` 后 CHA 的 INVALID_LENGTH 确实消失（B45，正结果），但暴露"随机坏链"。
8. **时钟域/跨 PLL 频漂** —— 两链时钟统一到 dsi0 PLL 后失败不变（B53）；pclk/byte 比值精确 4/3（B55）。
9. **DPU split / master-only 耦合** —— ABL 期 `SPLIT_DISPLAY_EN=0`，厂商耦合路线本机没用（B52）。

## ⚠️ 打包时发现的一个疑点（建议优先核实）

上一轮（B59/B60）把"pstore 读不到 panic"归因为 **`CONFIG_PSTORE_FS` 缺失**，并"补上"了它。但核实发现：

- 本内核 `fs/pstore/Kconfig` 里**根本没有 `PSTORE_FS` 这个符号**（只有 PSTORE / CONSOLE / PMSG /
  RAM / BLK / ZONE / FTRACE）。
- 实际构建的 `out/kernel-msmmod/.config` 里**完全没有 `PSTORE_FS` 这一行**
  （若符号存在但未启用，应出现 `# CONFIG_PSTORE_FS is not set`）。
- 源 config 里写的 `CONFIG_PSTORE_FS=y` 被 Kconfig 静默丢弃。

→ 结论：`CONFIG_PSTORE_FS` 在 7.2 内核里已不存在（pstore 的 `/sys/fs/pstore` 接口由 PSTORE 核心直接提供）。
**所以"补 PSTORE_FS 就能读到 panic"这个假设不成立**，pstore 读空另有原因
（更可能是 ramoops 区域在两次 boot 间被 ABL 踩，或 `/sys/fs/pstore` 未挂载）。

> 这条只是打包时的静态发现，**未上机验证**。建议顺手确认一次 `mount | grep pstore`
> 与 `ls /sys/fs/pstore`，能快速排除"没挂载"这条。
